## 1. What was read from production before writing anything

The retirement procedure is based on the live database, not on assumptions:

| Table | Rows | Last write |
| --- | --- | --- |
| `cleanings`, `cleaning_assignments`, `cleaning_events`, `cleaning_media`, `properties`, `property_access`, `property_instructions`, `expenses`, `payouts`, `organization_members` | 0 | — |
| `organizations` | 1 | 2026-08-31 (bootstrap) |
| `profiles` | 4 | **2026-10-01** |

`profiles` being written recently is the finding. The writer is not the application:

```
trigger on_auth_user_created on auth.users
  → private.handle_new_user()  (SECURITY DEFINER, search_path public)
  → insert into public.profiles (id, full_name) values (new.id, coalesce(new.raw_user_meta_data ->> 'full_name', ''))
```

Dropping `profiles` first would therefore break **every new sign-up**, including the self-registration added in this slice. `deployment/retire-legacy.sql` drops the trigger and the function first, asks for a sign-up to be proven afterwards, and only then drops the tables. The definition above is kept here so the trigger can be restored if anything goes wrong mid-procedure. No `st_*` table has a foreign key into any of those tables (the procedure re-checks that before dropping).

## 3. Node suites

**197 tests, all passing.** `tests/auth-boundary-contract.test.mjs` did its job: it failed as soon as `account/request` appeared before `context(req)`, which is exactly the trap it was written for. It was then extended rather than widened — it now asserts that the pre-auth set is exactly `bootstrap`, `dispatch/outbox` and `account/request`, and for the new one that it calls `authOnly(req)`, takes `p_auth_user_id` from `authUser.id` and `p_email` from `authUser.email` (never from the body), mentions no role, creates the account **inactive**, can be switched off through `selfRegistrationOpen`, and refuses an operations manager as the decider.

## 4. Browser suites

Two new blocks (22 PASS lines in `usability-browser` overall):

- **client self-registration: the form warns, sends the request, and an existing account is told to sign in** — the form states that accounts are checked by hand before anything is sent, requires a 12-character password, sends name, company and property count, shows "you will get an email as soon as the account is open", and for an address that already has an account shows "just sign in" instead of a silent failure.
- **account requests: queue, required reason to reject, optional note to approve, decided history** — the queue opens on `PENDING` and shows the company, email, phone, city and message; Clients carries its two tabs; rejecting with an empty reason sends **nothing** (the dialog shows its own error); with a reason it sends `{id, action:'reject', note}`; approving sends an empty note and names the account that was opened; and the `ALL` filter shows the rejected request with its reason.

A detail this caught in the tests themselves: Playwright's `name` matching is a substring, so the filter buttons "Approved"/"Rejected" also match "Approve"/"Reject" — the row buttons needed `exact: true`. Worth remembering for the next block.

All other browser suites, the preview check and the production bundle pass unchanged; the ru/uk/sk crawl is still at the three intentional English strings.

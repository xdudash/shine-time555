# Shine Time — аудит и проект переработки

Дата: 6 сентября 2026. Статус: первичный аудит и проект для согласования; реализация переработки ещё не выполнена.

## Проверенная основа

Изучена последняя найденная сборка `Shine_Time_Hostinger_Supabase_r1.zip` от 2 сентября и исходники действующей Supabase Edge Function `st-api`, версия 5. Серверные файлы `index.ts` и `logic.mjs` совпадают с архивом по содержанию; различается только завершающая пустая строка при локальном сохранении.

Подключён проект `shine-time-operations`, регион eu-central-1, PostgreSQL 17. Получен статус ACTIVE_HEALTHY. По метаданным таблиц: 3 пользователя приложения, 4 объекта, 7 заказов, 8 фото. Это не результат проверки фактического содержимого всех записей и не свидетельство масштабируемости. Во всех перечисленных таблицах включён RLS. Рабочие данные и настройки не изменялись.

Текущая архитектура: Hostinger обслуживает PHP-оболочку и PWA, Supabase предоставляет Auth, PostgreSQL, Edge Function, Storage и Realtime. Существуют роли ADMIN, OPERATIONS_MANAGER, CLEANER, OWNER, PROPERTY_MANAGER. GitHub-интеграция не вернула доступных репозиториев. Текущие файлы на самом Hostinger ещё не сопоставлены с архивом.

## Подтверждённые проблемы

| Приоритет | Наблюдение и источник | Последствие | Требуемое изменение |
|---|---|---|---|
| P0 | `hydrateJobs` в `st-api/index.ts` добавляет `access_instructions`, `key_instructions`, `wifi`, коммерческие поля; marketplace возвращает результат без фильтрации по назначению | Свободный заказ может раскрывать инструкции доступа ещё до назначения клинера | Раздельные серверные представления данных для рынка, назначенного исполнителя, клиента и администратора; тесты на отсутствие закрытых полей |
| P0 | Назначение админом, изменение статуса и завершение: проверка → отдельный UPDATE → отдельная запись события; UPDATE ограничен ID, без проверки версии/актуального назначения | Между проверкой и записью другой запрос может изменить заказ; возможны потеря изменений и частичный успех | Транзакционные команды с блокировками, проверкой актуального исполнителя/статуса, версией записи и ключом повторного запроса |
| P1 | `cleaner/availability` жёстко отклоняет время вне 10:00–15:00; marketplace обрезает доступность глобальным `windowEnd` | Вечерние и дневные объекты с собственным расписанием не работают согласно прежнему требованию | Окна объекта и доступность исполнителя; глобальное время только как начальное значение формы |
| P1 | `client/slots` передаёт заказы всех клинеров в общую проверку пересечений `availableBookingSlots` | Занятость одного клинера блокирует слот у всей команды | Расчёт свободного места по каждому исполнителю с учётом объекта, маршрута, длительности и резерва |
| P1 | `startLiveUpdates` вызывает полный `render()` после каждого события `st_jobs`; `render()` пересоздаёт оболочку и карту | Мерцание, лишние запросы, потеря состояния форм и гонки ответов | Стабильная оболочка, обновление затронутых данных, защита от устаревших ответов, восстановление после разрыва связи |
| P1 | История, заработок, финансы и годовой тренд читают наборы строк без явного обхода страниц | При достижении серверного ограничения ответа отчёт может оказаться неполным | Серверная агрегация, курсорная пагинация и контроль полноты экспорта |
| P1 | Фото передаётся base64 через общую Edge Function; загрузка файла и запись метаданных раздельны | Лишний трафик и память, риск файла без записи и повторной загрузки | Прямая разрешённая загрузка в приватное хранилище, проверка типа/размера, подтверждение загрузки, повторы и очистка незавершённых файлов |
| P1 | `sw.js` кэширует практически все GET-запросы, а не только разрешённую оболочку | Приватные медиа могут сохраняться дольше предполагаемого; политика выхода не определена | Белый список статических ресурсов; отдельная политика хранения приватных данных и очистка при выходе |
| P2 | `reschedule` последовательно переписывает расписание заказов отдельными запросами | План может обновиться частично; назначение и маршрут не являются единым результатом | Единая проверка и фиксация нового расписания либо явный отказ с объяснением |

P0 означает блокер запуска по безопасности/целостности. P1 — блокер заявленного массового операционного запуска. Это подтверждённые участки для исправления, а не завершённый аудит всей системы.

### Воспроизведение без изменения рабочей базы

Запущены существующие функции из серверного `logic.mjs` на синтетических данных через Node:

1. Два клинера доступны с 10:00 до 15:00; у первого заказ 10:00–11:00, второй свободен. Ожидание: слот 10:00 доступен. Факт: первый доступный слот — 11:00.
2. Клинер доступен до 19:00, заказ 16:00–17:00 с дедлайном 19:00. Факт: marketplace отклоняет его как выходящий за доступность при глобальном `windowEnd=15:00`.
3. Синтетическое поле `access_instructions` сохраняется в marketplace-ответе. В серверной цепочке это поле заполняется из объекта до передачи в marketplace.

Нагрузочные проверки, браузерные сценарии всех ролей и проверка восстановления базы ещё не выполнялись. Supabase Security Advisor вернул предупреждение об отключённой проверке скомпрометированных паролей; отсутствие других предупреждений не заменяет проверку прикладных прав. Справка: https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection

## Выбор подхода

| Подход | Преимущество | Недостаток |
|---|---|---|
| **Рекомендуется: поэтапная замена модулей с сохранением данных и контрактов** | Сохраняются аккаунты, объекты, история и полезные функции; каждый этап проверяем и откатываем | На переходном этапе требуется совместимость старого и нового клиента |
| Только локальные исправления существующего интерфейса | Быстрее закрывает отдельные ошибки | Не решает системно состояние экранов, финансовую модель и сопровождение |
| Полная замена приложения и базы с нуля | Свобода новой архитектуры | Повторяет риск потери функциональности и сложной миграции, который уже возникал |

## Целевой продукт

### Клинер

Мобильная главная «Моя смена»: доступность по дням, назначенные и доступные уборки, понятный заработок. Принятие заказа с серверной проверкой пересечений; адрес и навигация, защищённые инструкции доступа после назначения. Переходы «принял → в пути → прибыл → уборка → проверка/завершено». Чек-листы по объекту, фото и видео с прогрессом загрузки, сообщение о проблеме, запрос помощи и освобождение заказа по правилам. Повторная отправка после обрыва связи не создаёт дубль. Локально сохранённый черновик не показывается как подтверждённое сервером действие.

### Клиент и управляющий объектами

Собственные/назначенные объекты, инструкции, тарифы и отдельные окна обслуживания; разовые и повторяющиеся заказы, перенос/отмена с прозрачными правилами. Статус уборки, подтверждённый фотоотчёт, проблема и её решение, документы и история оплат. Управляющий работает только с явно назначенным портфелем; расходы исполнителей и внутренняя прибыль доступны по явно заданным полномочиям, а не через общий ответ API.

### Админ и операционный менеджер

Диспетчерский экран с заказами, исполнителями, сроками, фильтрами, картой и причинами риска. Ручное назначение и переназначение, массовые операции, рекомендации исполнителей с объяснением, резерв и срочная замена. План на день/неделю, повторяющиеся задания, категории объектов: посуточные квартиры, обычные квартиры/дома, офисы, подъезды и общие зоны. Чек-листы, длительность, стоимость и правила доступа задаются для объекта/услуги. Админ управляет аккаунтами, блокировками, правами, тарифами и причинами исключений; существенные действия записываются в журнал.

### Финансы

Отдельно учитывать стоимость услуги, начисление клинеру, бонус, доплату, расход, счёт, полученную оплату и фактическую выплату. Завершённая уборка не равна оплаченному счёту. Денежные суммы хранить точно; исправления проводить корректирующими записями с автором и причиной. Месячные отчёты, задолженности, ведомости выплат и выгрузки должны сходиться с журналом операций. Автоматические реальные списания и выплаты подключаются отдельным этапом после выбора платёжного провайдера; их нельзя обозначать работающими до проверки интеграции.

## Технический проект

- Сохранить Supabase как источник истины. Разделить серверный код по модулям: доступ, объекты, заказы/назначения, медиа/качество, финансы, уведомления.
- Сохранить Hostinger для совместимой оболочки на первом этапе. Решение о переносе отдачи интерфейса принимать по измерениям, не по предположению, что текущий тариф выдержит любую нагрузку.
- Все команды над заказом выполняются транзакционно: актуальные права → проверка версии/состояния → изменение → событие → запись задачи уведомления. Дубли команд возвращают прежний результат без повторного начисления.
- SQL-блокировки упорядочить, чтобы назначения и переназначения не приводили к взаимным блокировкам. Повторное завершение и действия прежнего клинера после переназначения отклонять корректно.
- Для масштабирования по городам/командам использовать явную принадлежность и доступ; не включать автоматически всех текущих пользователей в новые области данных. Существующие записи сохраняют идентичность при миграции.
- Realtime сообщает об изменениях конкретных сущностей. Клиент объединяет частые события, перечитывает только нужные данные и восстанавливает пропущенные изменения после переподключения. Чек-листы, проблемы, уведомления и доступность тоже имеют механизм актуализации.
- Бизнес-правила времени привязать к Europe/Bratislava на первом рынке; календарная дата услуги отделена от UTC-времени события. Перевод часов и переход через полночь проверять явно.
- Фоновые задачи: уведомления, повторяющиеся заказы, напоминания, обработка медиа и экспорт. Для каждой — идемпотентность, ограниченные повторы и видимость неуспеха оператору.
- Воспроизводимая сборка, закреплённые версии зависимостей, отдельная среда проверки, журнал ошибок и метрик, резервное копирование и отработанный откат.

## Порядок реализации

1. **Надёжное ядро:** закрыть выдачу инструкций в marketplace, убрать глобальный запрет времени, исправить слоты, транзакционные назначения/статусы/завершение и проверки прав. Сначала добавить тесты, воспроизводящие ошибки.
2. **Клинер и диспетчер:** стабильные экраны, назначенные работы, сохранение формы, фото/видео и проблемы, актуализация без полной перерисовки. Проверить две параллельные сессии.
3. **Объекты и клиент:** все категории, окна, повторяемость, бронирование и правила портфеля, отчёты и отмены.
4. **Финансы и управление:** журнал операций, счета/оплаты/выплаты, точные отчёты, права админа и аудит.
5. **Подготовка запуска:** миграция на копии, тесты нагрузки и связи, проверка восстановления, ограниченный пилот и контролируемый выпуск.

Каждый этап заканчивается работающим проверяемым результатом. Старые таблицы и функции не удаляются до проверки переноса соответствующих сценариев.

## Критерии готовности

Это проектные цели, а не уже подтверждённые характеристики. Начальная цель: 500 одновременно подключённых сессий, 100 одновременно выполняемых уборок, 1 000 заказов в день; далее нагрузка увеличивается ступенями по результатам измерений и бюджету инфраструктуры.

| Область | Приёмка |
|---|---|
| Конкурентность | Из 50 одновременных попыток принять один заказ успешна ровно одна; отмена, переназначение и завершение не портят состояние; повторы не дублируют начисления |
| Права | Для каждой из пяти ролей проверены разрешённые и запрещённые операции; чужие объекты, закрытые инструкции и финансовые поля недоступны через прямой API |
| Расписание | Работают окна вне 10–15, несколько свободных клинеров, буфер дороги, индивидуальная длительность и отказ при настоящем пересечении |
| Интерфейс | Форма и загрузка медиа сохраняют состояние при входящих событиях; устаревший ответ не заменяет новую страницу; есть понятные состояния ошибки и переподключения |
| Масштаб | На тестовой инфраструктуре при целевой нагрузке p95 чтения обычного экрана ≤1,5 с, команды ≤2 с, распространения изменения ≤2 с; доля неожиданных ошибок <0,5%. Замеры отдельно по серверу и браузеру |
| Полнота данных | Отчёты и экспорт проверены на объёме свыше лимита одного API-ответа, с синтетической историей не менее 100 000 заказов |
| Надёжность | Обрыв сети при принятии, завершении и загрузке не создаёт дублей; задачи с ошибкой видны и повторяются контролируемо |
| Восстановление | Восстановление копии БД и медиа выполнено в тестовой среде; измерены фактические RPO/RTO и согласованы перед запуском |
| Выпуск | Пройдены сценарии админ → клиент → назначение → клинер → отчёт → начисление; есть список оставшихся ограничений и проверенный откат |

Обозначение «готово к запуску» допустимо только после этих проверок на выбранной инфраструктуре. Сходство интерфейса с Uber само по себе не является критерием готовности.
